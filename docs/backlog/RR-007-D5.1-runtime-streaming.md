# RR-007 D5.1 — Runtime streaming and pooling

## Objective

Maintain a bounded, deterministic window of authored world segments around the player and reuse segment instances safely to reduce allocation churn during an endless run.

## Scope

- Explicit streaming API: `stream_around_player(player)`; optional automatic driving through `streaming_enabled` and `player_path`.
- Keep a configurable number of segments behind and ahead of the nearest segment midpoint.
- Recycle segments that fall behind the retention window.
- Pool instances by stable `segment_id`; never reuse an instance for a different definition.
- Bound pool memory with `max_pooled_segments`; excess instances are freed.
- Preserve the generated segment definition metadata and connector alignment when reusing instances.
- Optional scene lifecycle hooks:
  - `prepare_for_pool()`: stop transient work, clear temporary state and detach external registrations before storage.
  - `reset_from_pool()`: restore authored runtime state after placement and before use.
  - `on_segment_activated()`: resume segment-specific runtime behavior after activation.
- Existing scenes without hooks remain supported, but mutable gameplay state in those scenes is not automatically reset.

## Runtime contract

The generator owns segment lifetime while a segment is active or pooled. Systems that create transient children, timers, signal connections outside the segment, audio, particles, or gameplay registrations must clean them up in `prepare_for_pool()` and restore their authored defaults in `reset_from_pool()`. A pooled segment is detached from the active world, hidden, and has processing disabled. Pool capacity is a hard upper bound; setting it to zero disables retention.

Streaming uses the nearest authored entry/exit midpoint to identify the player's current segment. Segment scenes are expected to be linear modular pieces with entry/exit sockets; curved-world progress tracking is not part of D5.1.

## Automated validation

- Initial active window is created from a fixed seed.
- Advancing the player recycles segments behind the retention window.
- New segments are appended to maintain the configured ahead count.
- Reuse is restricted to the same segment definition.
- Active count and pool count remain bounded.
- Clearing the generator frees active and pooled instances.

## Acceptance boundary

CI tests validate deterministic bookkeeping, lifecycle, and pooling behavior. They do not prove frame-time improvements, memory stability on target devices, visual seam quality, or reset correctness for future scene-specific mutable systems. Those require profiler captures and playtesting on target Android devices in later D5 validation.
